# Журнал бектестів

Ця тека — **історія еволюції стратегії**: кожен звіт показує, який параметр
змінювався, на яких даних і з яким результатом. Разом із git-історією це доказ
власної розробки та обґрунтованості кожного рішення (STRATEGY.md §14 — вимога
Funding Pips до самостійно написаних роботів).

## Що потрапляє в git

| Файл | У git | Чому |
|---|---|---|
| `backtest_<tag>.txt` | ✅ так | зведений звіт: WinRate, PF, expectancy, DD, помісячний PnL |
| `trades_<tag>.csv` | ❌ ні | десятки тисяч рядків, відтворюється прогоном бектесту |

Правила — у [.gitignore](../.gitignore) (`reports/*` + винятки на `*.txt`).

## Конвенція іменування

```
backtest_<що_перевіряємо>.txt
```

Тег має відповідати на питання «яка це гіпотеза», а не «коли я це запустив»:

- `baseline_1R` — базова модель без фільтрів, `fixed_rr: 1.0`
- `rr_1_5` — той самий період, змінено лише `targets.fixed_rr` на 1.5
- `trailing_05_05` — `tp_mode: trailing`, `trail_start_r 0.5`, `trail_step_r 0.5`
- `rvol_1_0` — увімкнено `filters.min_or_rvol: 1.0` поверх найкращого базлайну
- `wf_train_2025H1` / `wf_test_2025H2` — walk-forward: навчання / перевірка

**Один прогін = одна зміна параметра** (STRATEGY.md §15 і застереження від
оверфітингу в §7). Kitchen-sink із усіх фільтрів одразу — не гіпотеза, а шум.

## Важливе застереження

Звіт має сенс лише разом із контекстом прогону. Перед тим як показувати
результати комусь (у т.ч. проп-фірмі), переконайся, що вказано:

1. **джерело даних** — брокер і символ (`GER40` у Funding Pips ≠ `FDAX` у першоджерела);
2. **витрати** — `backtest.spread_points`, `slippage_points`, `commission_per_lot`
   з config.yaml на момент прогону (заміряні у своєї фірми, а не дефолтні);
3. **період** — і чи це in-sample (навчання) чи out-of-sample (перевірка).

Прогін без реальних брокерських даних і реального спреду — інженерна перевірка,
а не підстава для торгівлі реальними грошима.
